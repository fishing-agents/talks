## Executive findings

- **AMD ROCm:** `amd-device-plugin` does not implement a Prometheus exporter. Its optional per-GPU health path is a client of AMD's separate Device Metrics Exporter, using a Unix gRPC socket. The first-party install guide documents the external exporter chart, a ClusterIP port 5000, and the socket, but does not define its Prometheus metric schema. Plugin fallback health remains available if that service/socket/RPC is unavailable. AMD SMI in the device plugin resolves UUIDs and product names by BDF; it is not used there to collect utilization, memory, temperature, or power. `amd-hami-core` is an in-process HIP interception/enforcement library, not an exporter.
- **Ascend:** `ascend-device-plugin` contains an actual Prometheus endpoint on `:9395/metrics` for HAMivNPUCore and ENPU modes. It emits physical-device and workload-attributed series. Most Hami-vNPU tenant memory comes from shared memory written by `hami-vnpu-core`; ENPU memory attribution uses DCMI process data plus host `/proc` cgroup lookup. A named tenant utilization metric is currently the physical device AICore percentage copied onto each allocation, not measured tenant utilization. Context/module/buffer memory series are hardcoded zero. The legacy whole-card/template mode does not start this server. ENPU docs include a PodMonitor example; the checked-in daemonset names port 9395 `monitorport`.
- **Ascend DRA:** the DRA driver discovers devices/capacities and allocates claims, but no Prometheus collector was found in its first-party Go/chart implementation. Its optional gRPC healthcheck is not a metrics endpoint and is disabled by default (`healthcheck-port=-1`).
- **Biren:** the first-party plugin reports device inventory/health to Kubernetes/HAMi and logs allocation/heartbeat activity. No telemetry exporter, metric names, scrape port, or tenant utilization/memory telemetry were found.
- **Hygon DCU:** the standalone `dcu-exporter` is a real Prometheus exporter on `/metrics`, default port 16080, polling the DCU DCGM package every 10 seconds. It exports physical and virtual-device gauges and associates workload labels via kubelet PodResources and virtual-device config files. The `dcu-dcgm` repository is a lower-level ROCm-SMI/HY-DMI binding plus JSON HTTP API (default port 16081), not a Prometheus exporter. The `dcu-vgpu-device-plugin` consumes DCGM for device inventory/sharing but has no metrics endpoint; this repository is archived.

## Per-repository inventory

### 1. `amd-device-plugin` - optional AMD exporter client, not exporter

- **Implemented:** First-party code reads AMD SMI UUID and ASIC market name for PCI BDF identity; the CGo linkage is to `amd_smi`. The AMD SMI calls here are `amdsmi_get_gpu_device_uuid` and `amdsmi_get_gpu_asic_info`, not sampling telemetry. The plugin health code checks `/var/lib/amd-metrics-exporter/amdgpu_device_metrics_exporter_grpc.socket`, uses gRPC `List`, and maps GPU health onto device-plugin health. If unavailable, it uses the simple health result. [AMD SMI identity code, lines 3-6 and 73-150](https://github.com/Project-HAMi/amd-device-plugin/blob/9a3e617def1f0a22d023e1cc2a5398ebd9283a5f/internal/pkg/amdgpu/amdsmi.go#L3-L6) [health client/fallback, lines 35-105](https://github.com/Project-HAMi/amd-device-plugin/blob/9a3e617def1f0a22d023e1cc2a5398ebd9283a5f/internal/pkg/exporter/health.go#L35-L105) [plugin heartbeat health update, lines 522-548](https://github.com/Project-HAMi/amd-device-plugin/blob/9a3e617def1f0a22d023e1cc2a5398ebd9283a5f/internal/pkg/plugin/plugin.go#L522-L548)
- **Docs claim/readiness:** The installation guide says health checks require AMD Device Metrics Exporter, documents its `ClusterIP` service port `5000`, enables the Unix socket at the same path above, and installs external chart v1.2.0. This port is documented as the exporter's service port; the plugin's health transport is the Unix socket. The guide does not document the external exporter's exact metric list, labels, units, or `/metrics` path. [External exporter install and socket configuration, lines 58-104](https://github.com/Project-HAMi/amd-device-plugin/blob/9a3e617def1f0a22d023e1cc2a5398ebd9283a5f/docs/user-guide/installation.md#L58-L104)
- **Metrics/tenant visibility:** No first-party Prometheus `Collector`, `/metrics` handler, telemetry metric declarations, per-process/tenant usage output, or exporter port is implemented in this repository. Per-device health is not a telemetry metric. Exporter absence degrades to simple health rather than disabling the plugin.
- **Logs/events/gaps:** Plugin uses glog for startup, health and errors. This repository does not bridge AMD events, temperature, power, or tenant telemetry into its own scrape API. Any broader metrics schema is an **external vendor dependency**, not a HAMi implementation claim.

### 2. `amd-hami-core` - ROCm/HIP resource enforcement, no observability surface

- **Implemented/docs:** README describes `libamvgpu.so` as an LD_AUDIT library intercepting `hipMalloc`, `hipFree`, and `hipMemGetInfo` to enforce memory and CU-mask limits. Its user-facing log control is `LIBHIP_LOG_LEVEL` (ERROR/WARN/INFO/DEBUG). This is enforcement behavior, not telemetry export. [README feature/build and usage, lines 1-6, 23-56](https://github.com/Project-HAMi/amd-hami-core/blob/050cd7341dfe447483f087494fd0259eacd2006e/README.md#L1-L6) [log-level setting, lines 49-56](https://github.com/Project-HAMi/amd-hami-core/blob/050cd7341dfe447483f087494fd0259eacd2006e/README.md#L49-L56)
- **Metrics/visibility:** No Prometheus metric definitions, scrape endpoint, collector, health API, event exporter, or labels/units were found in first-party files. Shared control state and internal activity are not an exported observability interface.
- **Dependencies/gaps:** Requires ROCm and hardware for runtime enforcement; README's tested hardware/version statements are project documentation, not independently validated here. The core's memory/CU enforcement logs should not be presented as tenant usage metrics.

### 3. `ascend-device-plugin` - Prometheus exporter for vNPUCore and ENPU

### 5. `hami-vnpu-core` - shared accounting state consumed elsewhere, no exporter

- **Implemented/docs:** This Rust in-container library intercepts Ascend NPU runtime calls to enforce memory quota and compute time-sharing. Its shared memory records local `memory_limit`, `memory_used`, `compute_priority`, active workers and per-process per-device HBM bytes. The Ascend device plugin reads the layout; this repository itself does not expose these fields over HTTP/Prometheus. [README purpose and features, lines 1-14](https://github.com/Project-HAMi/hami-vnpu-core/blob/962cb4867ee543ab0357ed90f4c27ae18d5d2198/README.md#L1-L14) [shared state and process HBM fields, lines 49-98](https://github.com/Project-HAMi/hami-vnpu-core/blob/962cb4867ee543ab0357ed90f4c27ae18d5d2198/crates/limiter/src/shmem/mod.rs#L49-L98)
- **Metrics/tenant visibility:** No standalone collector, port, metric names/labels, event endpoint, or scrape readiness mechanism found. Tenant usage is visible only when paired with the `ascend-device-plugin` collector and its matching shared-memory/UUID mapping.
- **Logs/gaps:** README documents preload/runtime setup and quota/priority environment variables; it does not specify an operational telemetry or event schema. Resource accounting state should not be described as externally scrapeable by itself.

- **Units/interpretation:** `_bytes` names declare byte quantities; `dcu_pciebw_mb` is based on a source field documented as MB/s. `dcu_utilizationrate` and `vdcu_utilizationrate` are utilization percentages according to the underlying DCGM device structs. `dcu_temp`, `*_power*`, `*_sclk`, `dcu_memory_remaining`, and virtual metric units are not encoded consistently in Prometheus HELP text (which is generic) or metric suffixes; exporter copies underlying numeric fields without conversion. [source field descriptions, lines 754-799](https://github.com/Project-HAMi/dcu-dcgm/blob/e8fdd4be5e29b5cfc5133707c7e3da24479934bb/pkg/dcgm/structs.go#L754-L799) [gauge names and generic HELP, lines 44-142](https://github.com/Project-HAMi/dcu-exporter/blob/30408d074cd420729f5698710d54fb30abefb0b1/main.go#L44-L142)

## Proposed work (not implemented by the audited repositories)

1. Publish a vendor-neutral metric contract with explicit SI/binary units, physical-vs-virtual scope, stable hardware UUID labels, workload attribution semantics, and per-collector success/error gauges.
2. For AMD, document the external AMD Device Metrics Exporter's metric schema and scrape path separately from the plugin's Unix-socket health contract; clearly label vendor-managed data as a dependency.
3. For Ascend, rename percent-valued `*_ratio` series or normalize to 0-1, label physical utilization accurately, replace hardcoded zero memory subdivisions with real data or remove them, and expose per-collector failures consistently.
4. For Hygon, improve HELP/unit metadata, validate PodResources-to-device identity joins, and define whether physical gauges with pod labels are allocation context or tenant-attributed usage.
5. Add exporter/network-policy/readiness guidance where an endpoint exists; do not treat device-plugin health, resource registration, allocation state, or DRA liveness as hardware telemetry.
