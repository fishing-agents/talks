## 1. HAMi (scheduler + device-plugin-side vGPU monitor)

### Scheduler metrics: allocated/accounting state, not physical utilization

Implemented in a custom Prometheus collector built from the scheduler's in-memory `InspectAllNodesUsage`, quota, pod, leader and cache state. The scheduler creates one scrape-time snapshot and emits a `zone="vGPU"` constant label on collector metrics. Byte metrics convert the scheduler's MiB accounting values to bytes. The two `*_core_*_ratio` family values are **not consistently normalized fractions**: non-AMD values pass through as the scheduler's `Totalcore`/`Usedcores` accounting values (not normalized by this exporter; their scale is configuration/device-model dependent), while AMD values are normalized to 0-100. Only `hami_node_gpu_memory_allocated_ratio` is explicitly 0-1. Avoid graphing all names ending `_ratio` on one common fractional axis without a vendor-aware transform. [Collector and units](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/cmd/scheduler/metrics.go#L64-L74) [Descriptors and labels](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/cmd/scheduler/metrics.go#L157-L200) [Emission and conversions](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/cmd/scheduler/metrics.go#L305-L328)

| Default metric family | Value / labels |
|---|---|
| `hami_gpu_memory_limit_bytes`, `hami_gpu_memory_allocated_bytes` | Gauge, bytes; node/device identity labels. Allocated descriptor additionally has `device_cores`. |
| `hami_gpu_core_limit_ratio`, `hami_gpu_core_allocated_ratio` | Gauge, core accounting values; labels `node,device_uuid,device_index,device_type`. Unit caveat above. |
| `hami_gpu_shared_count` | Gauge, containers allocated/sharing a device; node/device labels. |
| `hami_node_gpu_overview` | Gauge with allocated bytes as value; capacity fields are labels (`device_cores`, `device_memory_limit`) with node/device identity. |
| `hami_node_gpu_memory_allocated_ratio` | Gauge, fraction 0-1; node/device identity. |
| `hami_node_gpu_mig_instance_info` | Info-style gauge 1 for runtime-ready MIG allocations; node, UUID/index, MIG UUID/profile/GI/CI and placement labels. |
| `hami_resource_quota_used`, `hami_resource_quota_limit` | Gauge of quota resource units (not a universal GPU unit); used labels `namespace,quota_name,limit`; limit labels `namespace,quota_name`. |
| `hami_vgpu_memory_allocated_bytes`, `hami_vgpu_core_allocated_ratio` | Per scheduled pod/device accounting gauge; bytes and core accounting respectively; labels `namespace,node,pod,device_uuid`. Scheduler collapses init-container usage; not a per-live-container split. |
| `hami_remote_gpu_memory_limit_bytes`, `hami_remote_gpu_allocated`, `hami_remote_gpu_overview` | Remote-pool limit/overview in bytes; allocation is 0/1. Labels identify server, endpoint, UUID/index and type (overview adds capacity labels). |

| `hami_build_info` | Gauge 1; constant labels `version,revision,build_date,go_version,compiler,platform`. |

### Device-plugin-side vGPU monitor: runtime/host data

Implemented in `cmd/vGPUmonitor`; custom registry serves `/metrics` at `:9394` by default (`--metrics-bind-address` overrides). It registers build-info and its own collector; standard Go/process collectors are explicitly commented out. [Flags, listener, registry and HTTP route](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/cmd/vGPUmonitor/main.go#L57-L66) [registry/metrics handler](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/cmd/vGPUmonitor/main.go#L148-L184).

| Default metric family | Value / labels |
|---|---|
| `hami_host_gpu_memory_used_bytes` | NVML host device used memory, bytes. |
| `hami_host_gpu_utilization_ratio`, `hami_host_gpu_memory_controller_utilization_ratio` | NVML core and memory-controller utilization, 0-100 percent (despite `_ratio`). |
| `hami_host_gpu_temperature_celsius`, `hami_host_gpu_power_usage_watts` | Host temperature Celsius; power watts. |
| `hami_host_gpu_ecc_errors_total` | Lifetime aggregate ECC count, labeled `error_type`. |
| `hami_vgpu_memory_used_bytes`, `hami_vgpu_memory_limit_bytes` | Per-container/per-vdevice used and configured limit, bytes. |
| `hami_container_device_memory_bytes` | Memory used, bytes; current labels are `namespace,pod,container,vdevice_index,device_uuid`. Older breakdown-as-label representations are a separate legacy contract. |
| `hami_container_device_utilization_ratio` | Per-vdevice SM utilization from HAMi-core cache. |
| `hami_container_last_kernel_elapsed_seconds` | Seconds since last kernel, omitted when source value is zero. |
| `hami_vgpu_memory_context_bytes`, `hami_vgpu_memory_module_bytes`, `hami_vgpu_memory_buffer_bytes` | Per-vdevice memory breakdown, bytes. |
| `hami_mig_device_info` | Gauge 1 with pod/container, device, MIG UUID/profile/GI/CI identity labels (see scrape caveat below). |

Host label set is `node,device_index,device_uuid,device_type`; vGPU/container label set is `namespace,pod,container,vdevice_index,device_uuid`; the collector adds constant `zone="vGPU"`. Names, HELP strings and labels: [metric descriptors](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/cmd/vGPUmonitor/metrics.go#L53-L140) [constant zone and collector setup](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/cmd/vGPUmonitor/metrics.go#L696-L732). Host measurements use NVML; container values are read from the HAMi-core usage cache [collector](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/cmd/vGPUmonitor/metrics.go#L237-L262) [cache values and emitted gauges](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/cmd/vGPUmonitor/metrics.go#L407-L465).

**Scraping:** Scheduler binds `/metrics` at `:9395` by default; its Service exposes monitor port 31993 and targets the named `metrics` container port. The vGPU monitor binds `:9394`; chart has its metrics Service. Helm provides scheduler and device-plugin ServiceMonitors only when the Prometheus Operator API is discoverable and `.Values.prometheus.enabled`; endpoints use `/metrics`. [scheduler bind default](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/cmd/scheduler/main.go#L68-L78) [scheduler ServiceMonitor](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/charts/hami/templates/scheduler/servicemonitor.yaml#L1-L23) [device-plugin ServiceMonitor](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/charts/hami/templates/device-plugin/servicemonitor.yaml#L1-L23) [scheduler Service monitor port](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/charts/hami/templates/scheduler/service.yaml#L15-L35) [vGPU monitor Service](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/charts/hami/templates/device-plugin/monitorservice.yaml#L1-L28).

**Shared-memory mechanism and failure modes:** HAMi-core exports `CUDA_DEVICE_MEMORY_SHARED_CACHE`, with `/tmp/cudevshr.cache` fallback; when unset it can synthesize `.../containers/<podUID>_<container>/usage.cache` using `CONTAINER_VGPU_MOUNT`, `POD_UID`, `CONTAINER_NAME`, then opens/maps the file `MAP_SHARED`. The mapped region contains atomic per-device memory/SM usage and process slots. [shared-region env/struct](https://github.com/Project-HAMi/HAMi-core/blob/ec5d85a3d709e5ed138a1668ebfefd366c05ca1e/src/multiprocess/multiprocess_memory_limit.h#L26-L41) [atomic usage structures](https://github.com/Project-HAMi/HAMi-core/blob/ec5d85a3d709e5ed138a1668ebfefd366c05ca1e/src/multiprocess/multiprocess_memory_limit.h#L70-L95) [cache path fallbacks and shared mmap](https://github.com/Project-HAMi/HAMi-core/blob/ec5d85a3d709e5ed138a1668ebfefd366c05ca1e/src/multiprocess/multiprocess_memory_limit.c#L1280-L1369). Bad path/permissions, absent or stale files, uninitialized cache, malformed version/magic, missing device UUID, or informer/API errors suppress container series; inspect monitor logs. [refresh/error handling](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/pkg/monitor/nvidia/cudevshr.go#L194-L268) [cache validation/mmap](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/pkg/monitor/nvidia/cudevshr.go#L317-L391) [per-scrape error policy and no UUID behavior](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/cmd/vGPUmonitor/metrics.go#L237-L262) [UUID/metric omissions](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/cmd/vGPUmonitor/metrics.go#L407-L465).

No missing-descriptor defect is established by this audit. Hardware/runtime scrape compatibility remains untested. [event recorder outcomes](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/pkg/scheduler/event.go#L61-L96) [scheduler state/outcome metrics](https://github.com/Project-HAMi/HAMi/blob/39699df26042b3e5062a76e00b3e4f74b72ad503/cmd/scheduler/metrics.go#L506-L558).

## 2. HAMi-core

HAMi-core is the CUDA interposition/enforcement and shared-cache producer described above, not a Prometheus HTTP service. The first-party search of core `src/`, headers and docs found no Prometheus collector, metric descriptors, `/metrics` handler, scrape port, or scrape setup. Its observability is through its log macros and cache state. The shared state carries memory context/module/data/total, SM utilization and process identity/status; the monitor reads it. [shared cache constants/fields](https://github.com/Project-HAMi/HAMi-core/blob/ec5d85a3d709e5ed138a1668ebfefd366c05ca1e/src/multiprocess/multiprocess_memory_limit.h#L26-L41) [shared structures](https://github.com/Project-HAMi/HAMi-core/blob/ec5d85a3d709e5ed138a1668ebfefd366c05ca1e/src/multiprocess/multiprocess_memory_limit.h#L70-L101).

The fallback path emits warnings if the per-container path cannot be formed/created/opened; it falls back to `/tmp/cudevshr.cache` or fails initialization if fallback open/map also fails. This fallback can break correct per-container attribution when multiple processes share it. [fallback and `mmap(MAP_SHARED)` error logs](https://github.com/Project-HAMi/HAMi-core/blob/ec5d85a3d709e5ed138a1668ebfefd366c05ca1e/src/multiprocess/multiprocess_memory_limit.c#L1280-L1369). **Negative finding scope:** first-party core source/docs; no Prometheus/exporter/scrape setup found. Metrics observed via HAMi monitor are consumer-side, not metrics served by this repository.

## 4. k8s-dra-driver (kubelet DRA plugin)

This is the NVIDIA DRA node driver/health path, not the Prometheus monitor. The plugin exposes an optional **gRPC health service** configured by `--healthcheck-port` (default disabled at -1; zero selects a random port); it is not a Prometheus endpoint. [flag](https://github.com/Project-HAMi/k8s-dra-driver/blob/ddca6be79a96dcab684b8f4617a3360c5fb23679/cmd/hami-kubelet-plugin/main.go#L143-L155) [health check implementation](https://github.com/Project-HAMi/k8s-dra-driver/blob/ddca6be79a96dcab684b8f4617a3360c5fb23679/cmd/hami-kubelet-plugin/health.go#L121-L150).

**Implemented health observability:** NVML event monitor registers XID/ECC event types, but its run path processes only critical XID; GPU-lost/UUID failures mark devices unhealthy and other event-wait errors are retried/logged. It emits klog messages, not Prometheus series or Kubernetes Events. [NVML event registration](https://github.com/Project-HAMi/k8s-dra-driver/blob/ddca6be79a96dcab684b8f4617a3360c5fb23679/cmd/hami-kubelet-plugin/device_health.go#L67-L110) [event loop and XID path](https://github.com/Project-HAMi/k8s-dra-driver/blob/ddca6be79a96dcab684b8f4617a3360c5fb23679/cmd/hami-kubelet-plugin/device_health.go#L146-L204). On unhealthy notification the driver updates in-memory health and republishes a ResourceSlice without unhealthy devices. Source explicitly says publish failure is logged without retry, leaving API allocation state stale; repaired GPUs are not republished healthy until driver restart (no remediation loop). [resource slice update and failure caveat](https://github.com/Project-HAMi/k8s-dra-driver/blob/ddca6be79a96dcab684b8f4617a3360c5fb23679/cmd/hami-kubelet-plugin/driver.go#L442-L504).

**Allocation vs runtime:** DRA claim capacities are injected into container HAMi-core environment/cache settings through CDI edits, including `CUDA_DEVICE_MEMORY_SHARED_CACHE` and per-device limit env vars; this is enforcement setup, not a metric exporter. Current source has a TODO for SM limit-from-claim and a default `60`. [capacity to environment/CDI edits](https://github.com/Project-HAMi/k8s-dra-driver/blob/ddca6be79a96dcab684b8f4617a3360c5fb23679/cmd/hami-kubelet-plugin/hami_core.go#L202-L295).

**Negative finding scope:** first-party `cmd/hami-kubelet-plugin` source, health, driver, docs and tracked configuration search found no Prometheus collectors, metric names, `/metrics` HTTP handler, scrape ServiceMonitor or GPU usage series. Health is gRPC; native NVML/XID observations are logs and ResourceSlice health changes.

## 5. KAI-resource-isolator

KAI adapts the HAMi monitor path: the optional privileged node monitor reads host NVML plus HAMi-core shared-memory cache data and serves `/metrics` on `:9394` by default (configurable). [defaults/port/optional ServiceMonitor](https://github.com/Project-HAMi/KAI-resource-isolator/blob/09c0bb90b360503ac3ec5ca987d07fcae852ae0a/chart/kai-resource-isolator/values.yaml#L34-L67) [DaemonSet args, health probes, cache mount](https://github.com/Project-HAMi/KAI-resource-isolator/blob/09c0bb90b360503ac3ec5ca987d07fcae852ae0a/chart/kai-resource-isolator/templates/monitor-daemonset.yaml#L35-L92) [Service](https://github.com/Project-HAMi/KAI-resource-isolator/blob/09c0bb90b360503ac3ec5ca987d07fcae852ae0a/chart/kai-resource-isolator/templates/monitor-service.yaml#L1-L27) [ServiceMonitor](https://github.com/Project-HAMi/KAI-resource-isolator/blob/09c0bb90b360503ac3ec5ca987d07fcae852ae0a/chart/kai-resource-isolator/templates/monitor-servicemonitor.yaml#L1-L23).

Default `hami_*` names are:

| Metric family | Value/unit; labels |
|---|---|
| `hami_host_gpu_memory_used_bytes` | Host NVML memory, bytes; `device_index,device_uuid,device_type`. |
| `hami_host_gpu_utilization_ratio` | Host core utilization 0-100; same labels. |

## Cross-repository takeaways / slide-safe wording

1. **Allocation != usage.** HAMi scheduler gauges, DRA claim metrics, and remote-GPU reservation metrics describe scheduler/API accounting. For live host memory/utilization use the NVML-backed node monitor; for HAMi vGPU process attribution use cache-derived container series. These measure different things and can disagree by design or under failure.
2. **DRA split:** HAMi-DRA monitor is control-plane resource accounting; `k8s-dra-driver` is kubelet-side device preparation and health. Driver health is surfaced by gRPC check, klog and ResourceSlice publication, not Prometheus GPU time series. Publication failure can leave stale advertised health because there is no retry.
3. **Cache dependency:** HAMi and KAI container-level metrics depend on HAMi-core's shared file and node-local mount/configuration, pod identity joins and container runtime initialization. Empty container series do not imply zero usage; they can mean no cache yet, invalid cache, missing UUID, API/informer mismatch or file permissions.
4. **Metric hygiene:** HAMi and KAI use `_ratio` for 0-100 utilization; HAMi scheduler's NVIDIA core ratios are raw accounting values while DRA explicitly scales core values to 0-1. Annotate dashboards with units rather than trusting suffixes. Current HAMi MIG identity has a descriptor in Describe; live MIG scrape behavior remains untested.
5. **No hardware validation:** no GPU, cluster, Prometheus scrape, emitted exposition or NVML behavior was exercised. This report is pinned source analysis only.
