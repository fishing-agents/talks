# HAMi observability, dashboards, and workload-facing documentation audit

Static audit of the assigned repository snapshots. No repository files were edited and no clusters, Prometheus endpoints, dashboards, or workloads were run. GitHub links below pin the inspected commit and include source line ranges.

## Executive findings

- There are **two distinct Prometheus metric vocabularies and presentation paths** in this scope. The website Grafana dashboard consumes the HAMi scheduler/device-monitor series (`hami_gpu_*`, `hami_host_gpu_*`, `hami_container_device_*`, `hami_vgpu_*`) and optional NVIDIA DCGM. HAMi-WebUI separately queries `hami_container_*` allocation/usage and `hami_*` capacity/telemetry series, then exports a cache of its metrics. Do not copy PromQL between the dashboard and WebUI without mapping metric names, labels, units, and scrape targets. [Dashboard docs, lines 28-42, 101-128](https://github.com/Project-HAMi/website/blob/181dbd0e830b8ca190f6170284f3238c3597732d/docs/userguide/monitoring/grafana-dashboard.md#L28-L42) [Dashboard JSON, lines 97-108, 1120-1210](https://github.com/Project-HAMi/website/blob/181dbd0e830b8ca190f6170284f3238c3597732d/static/grafana/gpu-dashboard.json#L97-L108) [WebUI query contract, lines 1-13, 153-205](https://github.com/Project-HAMi/HAMi-WebUI/blob/846c0e2d3360cc7240bb61968e4cc7e3cea53443/packages/web/projects/vgpu/metrics/query-contract.mjs#L1-L13) [WebUI exporter, lines 52-66, 148-186](https://github.com/Project-HAMi/HAMi-WebUI/blob/846c0e2d3360cc7240bb61968e4cc7e3cea53443/server/internal/exporter/metrics.go#L52-L66)
- The Grafana instructions are comparatively actionable: they name the two HAMi endpoints/default NodePorts, include Operator and non-Operator scrape guidance, and explain import and optional DCGM. The static JSON is Prometheus-specific and its panels use classic HAMi metrics; the allocation docs also list separate DRA metric names, which the JSON does not query. The documented v2.10+ dashboard compatibility therefore should not be read as evidence that the same JSON covers HAMi-DRA. [Instructions, lines 19-26, 28-56, 58-99](https://github.com/Project-HAMi/website/blob/181dbd0e830b8ca190f6170284f3238c3597732d/docs/userguide/monitoring/grafana-dashboard.md#L19-L26) [DRA metrics, lines 27-42](https://github.com/Project-HAMi/website/blob/181dbd0e830b8ca190f6170284f3238c3597732d/docs/userguide/monitoring/device-allocation.md#L27-L42)
- Workload-facing observability is present: website tables document per-container and vGPU use; WebUI implements workload allocation and time-series queries with missing-data/coverage handling; an Ascend Volcano tutorial walks through its plugin metrics endpoint. These are not equivalent promises across every supported device backend.
- Website's device-support table documents stable HAMi scheduling/isolation support across NVIDIA, Cambricon, Hygon, Ascend, Iluvatar, Mthreads, MetaX, Enflame, Kunlunxin, Vastai, AMD, AWS Neuron, Biren, and Teco under validation. This does **not** establish metric/dashboard parity. The WebUI README names a smaller provider integration set (NVIDIA, Ascend, Hygon, Cambricon, MetaX), and its backend sources use differing inventory/telemetry inputs. Optional DCGM hardware panels are explicitly NVIDIA-specific. [Website matrix, lines 5-23, 37-61](https://github.com/Project-HAMi/website/blob/181dbd0e830b8ca190f6170284f3238c3597732d/docs/userguide/device-supported.md#L5-L23) [WebUI README, lines 14-27](https://github.com/Project-HAMi/HAMi-WebUI/blob/846c0e2d3360cc7240bb61968e4cc7e3cea53443/README.md#L14-L27) [DCGM metrics, lines 119-128](https://github.com/Project-HAMi/website/blob/181dbd0e830b8ca190f6170284f3238c3597732d/docs/userguide/monitoring/grafana-dashboard.md#L119-L128)

### HAMi-WebUI implementation and semantics

WebUI's PromQL contract declares allocation series `hami_container_vgpu_allocated`, `hami_container_vcore_allocated`, `hami_container_vmemory_allocated`; capacity/usage series `hami_core_size`, `hami_core_util_avg`, `hami_memory_size`, `hami_memory_used`; and per-workload `hami_container_core_util` / `hami_container_memory_used`. It builds rankings and cluster trends, groups by `provider` and device identity, averages duplicate exporter replicas, and explicitly excludes compute allocations whose value is unknown instead of showing a misleading partial aggregate. [Metric names and replica handling, lines 1-60](https://github.com/Project-HAMi/HAMi-WebUI/blob/846c0e2d3360cc7240bb61968e4cc7e3cea53443/packages/web/projects/vgpu/metrics/query-contract.mjs#L1-L60) [Allocation/top queries, lines 62-151](https://github.com/Project-HAMi/HAMi-WebUI/blob/846c0e2d3360cc7240bb61968e4cc7e3cea53443/packages/web/projects/vgpu/metrics/query-contract.mjs#L62-L151) [Task usage coverage requirements, lines 153-205](https://github.com/Project-HAMi/HAMi-WebUI/blob/846c0e2d3360cc7240bb61968e4cc7e3cea53443/packages/web/projects/vgpu/metrics/query-contract.mjs#L153-L205)

Task trends bind queries to the current Pod UID allocation identity, verify full expected physical-device and vGPU coverage, report compute and memory trends, and avoid converting absent results into zero. Tests cover coverage, valid real zeros, missing data, failures, and stale request races. [Task monitor query flow, lines 24-33, 61-131](https://github.com/Project-HAMi/HAMi-WebUI/blob/846c0e2d3360cc7240bb61968e4cc7e3cea53443/packages/web/projects/vgpu/views/task/admin/useTaskMonitoring.js#L24-L33) [Tests, lines 41-48, 74-135](https://github.com/Project-HAMi/HAMi-WebUI/blob/846c0e2d3360cc7240bb61968e4cc7e3cea53443/packages/web/projects/vgpu/views/task/admin/use-task-monitoring.test.mjs#L41-L48)

The server registers/exporter contract includes device allocation, physical metrics, container allocation/use, pool totals, component health, and WebUI metric-refresh health. WebUI chart `ServiceMonitor` scrapes its own backend `/metrics`; a separate optional HAMi ServiceMonitor selects device-plugin `monitorport`. These are separate scrape jobs from the external Prometheus-compatible API WebUI queries. [WebUI exporter registration and names, lines 7-50, 52-186](https://github.com/Project-HAMi/HAMi-WebUI/blob/846c0e2d3360cc7240bb61968e4cc7e3cea53443/server/internal/exporter/metrics.go#L7-L50) [Backend ServiceMonitor, lines 16-43](https://github.com/Project-HAMi/HAMi-WebUI/blob/846c0e2d3360cc7240bb61968e4cc7e3cea53443/charts/hami-webui/templates/servicemonitor.yaml#L16-L43) [HAMi device-plugin ServiceMonitor, lines 1-26](https://github.com/Project-HAMi/HAMi-WebUI/blob/846c0e2d3360cc7240bb61968e4cc7e3cea53443/charts/hami-webui/templates/hamiservicemonitor.yaml#L1-L26)

WebUI installation docs require a Prometheus-compatible HTTP API (Prometheus or VictoriaMetrics) for external mode, spell out the HAMi 2.9 metric-label rename boundary, say chart ServiceMonitors require Prometheus Operator/CRD, and warn that Pod readiness alone does not prove a Prometheus selected/scraped them. [Prereqs/version compatibility, lines 18-46](https://github.com/Project-HAMi/HAMi-WebUI/blob/846c0e2d3360cc7240bb61968e4cc7e3cea53443/docs/installation/helm/index.md#L18-L46) [External API install/ServiceMonitor labels, lines 62-109](https://github.com/Project-HAMi/HAMi-WebUI/blob/846c0e2d3360cc7240bb61968e4cc7e3cea53443/docs/installation/helm/index.md#L62-L109)

It includes Cambricon (MLU), Hygon (DCU), Huawei Ascend, Iluvatar, Mthreads, MetaX, Enflame, Kunlunxin, Vastai, AMD, AWS Neuron, Biren and Teco under validation. ## Suggested accuracy notes for downstream slide material

1. Separate **scheduled/allocated capacity**, **physical device telemetry**, and **workload/container usage**; they are different signals and have different collectors.
2. Name Prometheus targets explicitly: HAMi scheduler, HAMi device-plugin/vGPU monitor, WebUI backend exporter, and optional vendor exporters/DCGM. Do not collapse these into "scrape kubelet."
3. Show metric family + labels + units per data plane; classic HAMi and WebUI use distinct names/contracts, and DRA allocation names differ again.
4. Label the dashboard's DCGM panels "NVIDIA optional"; show other vendor availability as implementation-specific/unknown unless a concrete exporter+query path is documented.
5. Distinguish a WebUI provider integration (inventory/health/resource information) from full physical and per-workload time-series support. The current source material explicitly allows coverage to vary by device type.
